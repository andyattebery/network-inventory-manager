## Context

Today the same runtime deps come from three places, each resolving its own versions:

| Install | Where versions come from | requests / urllib3 today |
|---|---|---|
| network-01 (overlay, `final.callPackage`) | homelab's nixos-26.05 `python312Packages` @ `597283ad` | 2.33.1 / 2.6.3 |
| Docker image, CI `test` job | `pip install` against PyPI at build time | 2.34.2 / 2.8.0 |
| flake `packages.*`, devshell | this flake's nixpkgs lock `b7c2ada9` | 2.34.2 / 2.7.0 |

The deps are declared three times: `pyproject.toml`, `nix/package.nix:39-42,56-59`, `flake.nix:107-113`. The version
is written twice: `nix/package.nix:13` and `pyproject.toml:7`, by a post-release bot (`update-flake.yml`).

Nothing gates what network-01 deploys. `main` has no branch protection and no required checks, and has never had a
PR (GitHub API). homelab's `nim` input has no ref, so `nix flake update` takes whatever is at `main` HEAD. Today that
is the bot's `[skip ci]` commit, which CI never ran on. The tests inside the nix build are currently the only gate.

After this change:

- `uv.lock` is the only pin. uv2nix builds the package, overlay and devshell from it, and Docker and CI install from
  it.
- The version lives only in `pyproject.toml` and is bumped before tagging.
- CI advances a `release` branch only after a tag's whole run passes, and homelab follows that branch.

## Non-goals

- Python stays 3.12 (user).
- No VCS-derived version: `uv_build` rejects dynamic metadata (uv `crates/uv-build-backend/src/metadata.rs`:
  "Dynamic metadata is not supported").
- No change to `nix/module.nix`, `nix/op-cli.nix` or `op-cli.toml`.
- Some parts of Astral's `uv-docker-example` are not uv-specific and would change runtime behaviour: a non-root
  user (the op CLI needs a writable `HOME`) and `PYTHONUNBUFFERED`. They are not adopted here; see the backlog.

## Decisions (with sources)

1. **uv2nix structure**: `loadWorkspace`, `mkPyprojectOverlay { sourcePreference = "wheel"; }`,
   `pyproject-build-systems.overlays.wheel`, and `mkVirtualEnv`.
   - Source: the uv2nix `templates/hello-world/flake.nix` (master, 2026-10-16).
   - Wheels need no overrides here. The only binary deps are pyyaml 6.0.3 and charset-normalizer 3.5.2, and both
     ship cp312 manylinux x86_64/aarch64 and macOS arm64 wheels (PyPI). uv2nix adds `autoPatchelfHook` for Linux
     wheels (`lib/build.nix:510`).
2. **Tests are `passthru.tests.pytest` on the package and exposed as `checks.<linux>.pytest`.**
   - Source: uv2nix `patterns/testing.md`: "runtime & test dependencies are not available at build time. Tests should
     instead be implemented as separate derivations." That is the whole basis.
   - Corrected after review: an earlier version also cited the nixpkgs manual here, and that misread it. The manual
     (`passthru.chapter.md`, "Package tests") runs upstream tests in `checkPhase` and offers `passthru.tests` for
     additional ones. It also recommends a cheap in-build launch check (`versionCheckHook`) because packages can
     build yet fail to start. NIM's suite moved out of the build only because uv2nix cannot run it there.
   - The gate moves to the `release` branch (decision 11), so the package build no longer runs tests, and
     `nix/package.nix:51-55` is rewritten. CI's `nix flake check` builds `checks.x86_64-linux.pytest`.
3. **Shipping**: `mkApplication` (uv2nix `patterns/applications.md`), with `overrideAttrs` to add `makeWrapper` and the
   existing `wrapProgram … op`. That doc uses `overrideAttrs` for exactly this kind of addition. `meta.mainProgram` is
   set per uv2nix `patterns/meta.md`; `lib.getExe` in `module.nix:218` needs it.
4. **Source filtering is per package** with `lib.fileset.toSource` (uv2nix `patterns/source-filtering.md`, which
   warns that filtering `workspaceRoot` causes IFD).
   - Package src: `pyproject.toml` + `network_inventory_manager/`.
   - Test derivation src: those plus `tests/`.
5. **Devshell is uv2nix's template as written**: an editable venv (`mkEditablePyprojectOverlay`, `workspace.deps.all`),
   `pkgs.uv`, and its `UV_NO_SYNC`/`UV_PYTHON`/`UV_PYTHON_DOWNLOADS` env and shellHook. The existing `op` stays.
   - The template's `pkgs.uv` is fine even though it is older than the uv that writes the lock. uv's docs
     (`concepts/resolution.md`, "Lockfile versioning") say "Changes to the revision will not cause older versions of
     uv to error."
6. **Backend is `uv_build`, with `[tool.uv.build-backend] module-root = ""`** (uv `concepts/build-backend.md`: flat
   layout via `module-root`; the module name already normalizes to `network_inventory_manager`). It is what
   `uv init --package` writes. The package is pure Python: 13 tracked files, all `.py`.
   - Bound: uv's docs say `uv_build>=0.13.4,<0.14`, while uv2nix's template uses `>=0.11.0,<0.14.0` (commit
     `ddca81d`, "restore … lower bound").
   - Nix builds run `uv build --no-build-isolation` with the consumer's uv: 0.11.21 on 26.05. The backend comes from
     build-system-pkgs (`uv-build` 0.13.3).
   - Verification 8 builds network-01 with uv's bound. If that builds, use it; otherwise use uv2nix's and record why.
7. **Test deps are `uv add --dev`, i.e. `[dependency-groups] dev`.**
   - Source: uv `concepts/projects/dependencies.md` ("Development dependencies … will not be included in the project
     requirements when published"). The nix test venv uses `{ network-inventory-manager = [ "dev" ]; }`.
8. **`.python-version` comes from `uv python pin 3.12`** (uv `concepts/python-versions.md`). uv-managed CPython
   3.12.15 is already installed on this Mac.
9. **The Dockerfile follows uv's Docker guide**, sections "Non-editable installs", "Intermediate layers", "Caching" and
   "Compiling bytecode", and the "Installing uv" pin.
   - Builder: `python:3.12-slim` with `COPY --from=ghcr.io/astral-sh/uv:0.13.4 /uv /uvx /bin/`, and
     `ENV UV_COMPILE_BYTECODE=1 UV_LINK_MODE=copy UV_NO_DEV=1 UV_PYTHON_DOWNLOADS=0`.
   - First sync: `uv sync --locked --no-install-project --no-editable`, with cache, `uv.lock` and `pyproject.toml`
     mounts. Then `COPY . /app` and `uv sync --locked --no-editable`.
   - Runtime: `python:3.12-slim` (same base, as the guide requires) with the unchanged op block,
     `COPY --from=builder /app/.venv /app/.venv` and `ENV PATH="/app/.venv/bin:$PATH"`. `ENTRYPOINT`/`CMD` are
     unchanged.
   - `RUN --mount` needs BuildKit, which has been Docker's default builder since Engine 23 and is what CI's buildx
     uses.
10. **CI `test` job follows uv's GitHub Actions guide**: `astral-sh/setup-uv` with `version: "0.13.4"` (the guide calls
    pinning uv best practice) and `enable-cache: true`, then `uv sync --locked` and `uv run pytest tests`.
    - The action is pinned by its exact release tag `@v10.3.0`: no floating major tag exists (checked), and the repo
      pins its other actions by tag. The guide's examples pin by commit SHA; doing that would be a repo-wide change.
11. **A `release` branch gates deployment.**
    - Source: the nixpkgs model. README: expressions are distributed "when successful build and test criteria are
      met". CONTRIBUTING: "When a channel is updated, its corresponding branch is also updated to the same commit."
      homelab already follows `nixos-26.05` this way.
    - New `ci.yaml` job: `needs: [nix, github-release]` (which transitively needs `docker` and `test`), and skips
      pre-releases. It checks out the tag and runs `git push origin HEAD:refs/heads/release`. A non-fast-forward push
      is rejected by default, so the branch can't move backwards; re-dispatching an older tag fails that job.
    - homelab's input becomes `github:andyattebery/network-inventory-manager/release` (Nix manual: `github:` refs take
      a branch or tag). That edit is in homelab-infrastructure.
    - **Sequencing, to leave no ungated window** (this change takes tests out of the package build):
      1. Seed `release` at `ea985a8`, the commit homelab's lock already deploys:
         `git push origin ea985a8:refs/heads/release`.
      2. Switch homelab's input; its lock stays at `ea985a8`.
      3. Merge this change.
      4. Release 0.2.3, which fast-forwards `release`.

      Steps 1 and 2 are git and cross-repo writes, and each needs the user's words.
12. **Release = bump, then tag** (uv `guides/package.md`: "`uv version` … updating the version of your package before
    you publish it").
    - Steps: `uv version --bump patch --no-sync` rewrites `pyproject.toml` and re-locks. Commit, then tag
      `$(uv version --short)` and push.
    - Deleted: `update-flake.yml`, the `github-release` job's "Trigger flake update" step (`ci.yaml:132-136`) and its
      `actions: write` (`:108`).
    - A pyproject-only bump leaves `uv.lock` stale and breaks the next uv run (uv issue #7533).
    - **[no source]** The `docker` job gets one step that fails when `${TAG#v}` differs from
      `project.version`, read with tomllib (the idiom the Dockerfile already uses). This guards the one manual step:
      no bot fixes a forgotten bump any more. Remove it if unwanted.
13. **CA bundle (fact, no action).** On network-01, `requests` now uses the locked certifi wheel instead of nixpkgs'
    cacert, as the image already does. The only verified-TLS call there is GitHub: DSM and AdGuardHome are `http://`
    (homelab `hosts/network-01/default.nix:121-122`), and UniFi is `verify = False` (`api/unifi.py:19`).

## Enforced vs. exhortation

- **Structural**:
  - `uv sync --locked` in CI and in the image build.
  - CI's own promotion: the `release-branch` job runs only after that tag's test, nix (pytest) and docker jobs
    pass. On `workflow_dispatch` every gating job checks out `inputs.tag`; before review it tested the
    dispatching branch, which could promote a tag whose own tests failed (fixed). CI's push only
    fast-forwards (no `--force`).
  - The tag check.
  - The op pin and its check (unchanged).
- **Exhortation** (corrected after review; an earlier version called these structural):
  - "`release` moves only through CI, and only forward". Nothing on GitHub enforces either: `main` is
    unprotected, the repo has no rulesets, and anyone with push access can move or force-push `release`.
    A ruleset on `release` ("Block force pushes", "Restrict deletions"; a user action, see backlog) would make
    "only forward" structural. "Only through CI" stays exhortation; the seeding step itself is a manual push.
  - "Bump with `uv version`". A miss is caught by `--locked`.
  - "Deploy from `/release`". This needs the homelab edit, sequenced before the merge (decision 11). If the merge
    lands first, homelab following `main` has no gate at all.
- **Residual**:
  - CI tests against this flake's nixpkgs, not 26.05. The Python deps are identical via `uv.lock`; the interpreter
    patch version and stdenv differ.
  - No darwin builder.
  - The image only builds in CI on tags.
